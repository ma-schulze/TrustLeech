# Claim 3 - Precision (Part One)

These testcases evaluate the precision claims made in Section 5.3 of the paper. 
For this, this testcase first evaluates all policies, except for the memory dump (P1), which is put into a different claim due to the runtime needed to reproduce it.

To still be able to make claims about P1, we instead replace the full memory dump with a single memory page read.
Since the performance of the policies is compared to executing the same policies for the KVM LibVMI backend, the relative performance of two single page reads should be approximately equal to the relative performance of two full memory dumps. 

To reproduce these tests, execute the `run.sh` file accompanying this claim. 
This opens a new QEMU VM, using the images generated by the install script. 
Log into the VM using the username `root`.

To verify the claims, execute the following steps:


## Preamble:

### Network Connection 
This test case (and the following ones) will require two QEMU VMs to interact with each other via a simulated network connection, which we implemented using QEMU user networking. 


## Testcase 1. 

### TrustLeech Policies
First, this test case evaluates the precision of TrustLeech using various VMI policies (and their performance). 
For this, first inject TrustLeech in the QEMU environment:
```
modprobe trustleech
```

Next, we again have to connect a second VM hosting the VMI appliance:
For this, execute the `run_2.sh` script in another terminal which will open another QEMU instance.
Here, also login with `root`, then execute: 
```
cd /usr/bin 
./vmi_client_2
```
This will connect to the first VM and execute the policies. 
After each policy executed, the time it took for it to execute is printed in the second QEMU environment.

### KVM Policies 
As a comparator for the performance of the VMI policies, we also execute them with the existing Legacy KVM LibVMI backend. 
For this, we first restart the first QEMU container (ctrl+d, x; then re_run `run_qemu.sh`). 
Once started, we start a new VM using `virsh`:
```
virsh create /domain.xml
```
Next, wait a few minutes to guarantee that the VM is fully booted.
If the VM is not fully booted, this may screw the numbers, since an unequal number of kernel modules etc. would be loaded, leading to different execution times of the policies.
Then, execute the vmi client script from within the same QEMU environment: 
```
cd /usr/bin 
./vmi_client_2
```
This client will now connect to the KVM instance to execute the VMI policies.
